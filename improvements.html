01 — Test Strategy

E2E偏重から、多層のフィードバックループへ。

Observation

担当した開発環境ではUnit Testが未整備で、 品質確認がE2Eテストや後工程の確認に大きく依存していました。 比較的小さなロジックの不具合でも、 後工程まで進まないと検出しにくく、 フィードバックコストが高くなりやすい構造に問題意識を持ちました。

0
Unit Testが未整備だった担当環境
Problem

確認が後工程へ偏る

  • 小さな不具合でも検出が後工程になりやすい
  • E2Eは実行・保守コストが高い
  • 各テスト層が何を保証するかが曖昧
Proposal

テストの責務を層ごとに分離する

ロジックはUnit、API・DB・外部連携はIntegration、 主要業務フローはSystem / E2Eへ分ける。 E2Eをなくすのではなく、 E2Eでしか確認できない重要フローへ集中させる。

E2E主要な利用者フロー
System業務シナリオ・非機能
IntegrationAPI・DB・外部連携
Unitロジックを高速に検証
Expected Impact

早く、原因を局所化しやすいフィードバック

より早い不具合検知、失敗原因の局所化、E2Eの実行・保守負荷低減、 CIへの自動テスト統合を期待しました。

Trade-off

ピラミッドの形自体を目的にしない

Unit Testを増やすだけでは業務フローや統合部分の保証にはならないため、 変更リスクと対象責務に応じてテスト層を選択する必要があります。

Status: Proposed / Shared internally / Not implemented

02 — CI/CD

ローカル依存の品質確認を、共有CIのガードレールへ。

Observation

Lint自体は導入されていましたが、 各開発環境で安定して同じ条件で動く状態ではなく、 品質確認が個々のDeveloper環境に依存していました。 また、DDDを採用したアーキテクチャでも、 依存ルールから外れた実装が残ることがあり、 人のレビューだけで継続的に守ることには限界がありました。

デプロイ自体は自動化されている一方、 本番まで複数の環境・段階を通す必要があり、 CIと自動テストが十分でないため、 一つの修正でも同様の動作確認を複数回手作業で行う状態でした。

4×
一つの修正で繰り返していた動作確認の最大回数
Problem

CDがあっても、検証Toilが残る

  • Lint結果がDeveloper環境に依存
  • Architecture Ruleが継続検証されていない
  • 複数環境への反映ごとに同じ確認を繰り返す
Proposal

品質ルールをExecutableにする

PR / pushを起点に、Lint・Format・Unit / Integration Testを共有CIで実行し、 DDDの依存方向などのArchitecture Ruleも、 Architecture Testとして機械的に検証する。

Code ChangePR / push
→
Lint / Format同一条件
→
TestsUnit / Integration
→
ArchitectureDependency rules
→
Feedbackmerge前に検知
Expected Impact

人が見るべきレビューへ集中する

DeveloperごとのLint差異、Architecture Rule逸脱、反復的な手動確認を減らし、 レビューを仕様・設計・影響範囲など人が判断すべき観点へ寄せることを期待しました。

Related Implementation

Bevy_AWS_lesson

この改善案で考えた「変更検証から成果物保存までの自動化」を、 個人開発ではRust + Bevyを題材に実装し、 GitHub Actions → AWS → Windows Release build → S3 Artifact Freezeまで検証しました。

03 — Platform Engineering

改善を、「空いた時間」から守る。

Observation

開発基盤や開発プロセスを改善しようという動き自体は、 何度か生まれていました。 しかし改善活動は通常の機能開発との兼任で、 開発案件が逼迫すると優先順位が下がり、 活動が止まることが繰り返されていました。

また、効率化で一時的に余力が生まれても、 その時間は新規機能開発へ再配分されやすく、 技術負債の返済や開発環境の継続的改善に使うCapacityを 確保しにくい構造がありました。

∞
余り時間に依存すると、改善は継続しにくい
改善で生まれた余力がすべて新規開発へ再投入されるなら、 改善活動自身を持続させる余白は生まれない。
Problem

Improvement work has no protected capacity.

  • 改善活動が機能開発との兼任
  • 開発が逼迫すると改善から先に止まる
  • 技術負債返済やDevEx改善が継続責務になっていない
  • 改善が個人の善意に依存する
Proposal

改善責任とCapacityを明示する

通常の機能開発とは別に、開発環境、CI/CD、自動化、Observability、 技術負債改善へ継続的に責任を持つ主体と明示的なCapacityを確保する。 組織規模に応じてDedicated EngineerからPlatform / DevEx Teamへ段階的に広げる。

Product Team Aneeds / feedback
Product Team Bneeds / feedback
↓
Platform / Developer Experience

↓

Trade-off

専任化や標準化そのものを目的にしない

Platform側がすべてを抱えると新たなボトルネックになり、 過剰な標準化はProduct Teamの事情や選択肢を損なう可能性があります。 共通ガードレールとセルフサービスの境界を設計する必要があります。

Related Implementation

Reliable Development Platform
